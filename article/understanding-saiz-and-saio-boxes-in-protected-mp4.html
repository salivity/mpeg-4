Understanding saiz and saio Boxes in Protected MP4

In protected MPEG-4 (ISOBMFF) streams utilizing Common Encryption (CENC), the Sample Auxiliary Information Sizes box (saiz) and Sample Auxiliary Information Offsets box (saio) provide the indexing mechanism for per-sample encryption metadata. This article explains the technical roles of saiz and saio, why they are essential for Digital Rights Management (DRM) systems, and how media decoders use them to locate and parse Initialization Vectors (IVs) and subsample encryption mapping data.

The Role of Auxiliary Information in Protected Streams

Standard MPEG-4 streams store sample timing, size, and chunk offsets within standard box structures such as stsz, stts, and stco (or trun in fragmented MP4). However, when a stream is protected using Common Encryption (ISO/IEC 23001-7), decoders require additional per-sample metadata to decrypt the content, including:

  • Initialization Vectors (IVs): Cryptographic nonces required for AES counter (CTR) or cipher block chaining (CBC) decryption modes.
  • Subsample Encryption Maps: Byte-range definitions indicating which portions of a sample are encrypted and which remain in the clear (common in video streams where NAL unit headers remain unencrypted for parsing).

Because standard MP4 sample tables do not account for this dynamic DRM metadata, the ISO Base Media File Format specification introduced generic auxiliary information containers: saiz and saio.

Function of the saiz Box (Sample Auxiliary Information Sizes)

The saiz box specifies the exact size (in bytes) of the auxiliary data associated with each sample.

  • Uniform Data Sizes: If every sample in a track or fragment shares the exact same auxiliary data size (for instance, a fixed 8-byte or 16-byte IV with no subsample encryption), saiz defines a single default size parameter (default_sample_info_size), minimizing file overhead.
  • Variable Data Sizes: When samples require varying amounts of auxiliary data (such as variable subsample mapping tables), saiz contains an explicit array listing the byte size for each individual sample in order.

Function of the saio Box (Sample Auxiliary Information Offsets)

The saio box specifies the memory location or file offset where the auxiliary information for each sample can be read.

  • Offset Mapping: It contains byte offsets pointing directly to the contiguous block of auxiliary data within the file or fragment.
  • Relative and Absolute Addressing: Offsets can be absolute within the entire file or relative to the start of an enclosing box (such as the moof box in fragmented MP4), allowing streaming clients to fetch encryption data without downloading unneeded media payloads.

How saiz and saio Work Together During Playback

When a DRM-enabled player or Decryptor processes an encrypted track, it follows a structured sequence:

  1. Identification: The player checks the aux_info_type and aux_info_type_parameter fields inside saiz and saio to confirm the auxiliary data represents CENC metadata (cenc or cbc1/cbcs).
  2. Offset Lookup: The player references the saio box to locate the start of the auxiliary data block.
  3. Size Parsing: The player reads the saiz box to calculate the boundary of the auxiliary data for sample \(N\).
  4. Metadata Extraction: The player reads the allocated bytes to extract the sample's specific IV and subsample count/ranges.
  5. Decryption: The Decryptor uses the extracted IV and subsample map alongside the decryption key obtained from the DRM license server to decrypt the protected sample bytes before passing them to the decoder.

Placement in File Structures

  • Standard (Non-Fragmented) MP4: Located inside the Track Box (moov/trak/mdia/minf/stbl), providing global indexing for the entire duration of the track.
  • Fragmented MP4 (fMP4 / DASH / HLS): Located inside each Track Fragment Box (moof/traf), providing local indexing specific to the samples packaged within that particular media fragment.
