How HTTP Byte-Range Requests Seek Inside MP4 Files

HTTP byte-range requests enable video players to stream and seek within unfragmented MPEG-4 (MP4) files efficiently without downloading the entire file first. By utilizing standard HTTP headers alongside the internal index structure of the MP4 container, web servers can serve isolated byte segments on demand. This mechanism allows a media client to map any arbitrary playback timestamp directly to a specific byte offset on the server, making instantaneous seeking possible over standard HTTP infrastructure.

The Structure of an Unfragmented MP4 File

An unfragmented MP4 file stores its data in hierarchical structures called "atoms" or "boxes." For seeking, two primary atoms are essential:

  • mdat (Media Data): Contains the raw audio and video payloads.
  • moov (Movie Metadata): Acts as the index for the entire file. It contains timing data, codec specifications, sample sizes, and crucial offset tables (stco or co64 for chunk offsets, stts for time-to-sample mappings, and stss for keyframe/sync-sample indices).

In an unfragmented MP4, the raw data inside the mdat atom is continuous and immutable, meaning individual video frames do not contain self-describing metadata. Instead, the player must consult the tables inside the moov atom to determine where any given frame lives in terms of file bytes.

The Role of HTTP 206 Partial Content

HTTP/1.1 introduced the Range request header (RFC 7233). When a web server supports byte-range requests, it advertises the Accept-Ranges: bytes header in its HTTP responses.

Instead of requesting a complete file via a standard GET request, a client can request a subset of bytes using:

Range: bytes=1048576-2097151

The web server parses these offsets, seeks directly to byte position 1048576 in the underlying file system, reads the requested segment, and returns it with an HTTP 206 Partial Content status code along with a Content-Range header.

How the Seeking Process Works

When a user initiates playback or jumps to a new timestamp in an unfragmented MP4, the client and server follow a specific sequence:

1. Metadata Retrieval

Before playback begins, the client requests the moov atom. If the moov atom is positioned at the beginning of the file (a "fast-start" optimized file), the client fetches the initial kilobyte range. If the moov atom is located at the end of the file, the client issues a HEAD request to learn the file size via Content-Length, then issues a byte-range request targeting the end of the file to download the metadata.

2. Time-to-Byte Translation

When a user seeks to a specific timestamp (e.g., 01:15):

  1. Identify Keyframe: The player reads the stss (Sync Sample Table) to find the nearest keyframe (I-frame) at or before 01:15, as video decoding must start from a keyframe.
  2. Calculate Byte Offset: Using the stco/co64 (Chunk Offset) and stsz (Sample Size) tables, the client calculates the precise byte offset in the mdat atom where that keyframe starts.

3. Fetching the Media Segment

Once the byte range is calculated:

  1. The client cancels any existing downloads.
  2. The client sends a new request to the server: 
    GET /video.mp4 HTTP/1.1
Host: example.com
Range: bytes=45281920-
  3. The server validates the range and returns an HTTP 206 Partial Content stream starting precisely at byte 45281920.
  4. The client feeds this incoming byte stream into the hardware or software decoder, achieving near-instantaneous playback from the desired point.

Why Metadata Placement Matters

For byte-range seeking to perform well on unfragmented MP4s, the moov atom should reside before the mdat atom. When the moov atom is placed at the end, the player must make an extra HTTP round trip to read the file's tail before it can decode any frames, increasing startup latency. Tools like FFmpeg resolve this using the -movflags faststart flag, which moves the moov atom to the front of the file.
