How MPEG-4 Decoders Process PCM Audio in MP4

An MPEG-4 system handles uncompressed Pulse Code Modulation (PCM) audio inside a standard MP4 (ISO Base Media File Format) container by relying on demuxer parsing, metadata extraction, and direct sample passthrough rather than traditional lossy decompression algorithms. Because PCM represents raw, uncompressed audio data, the decoder’s primary task is to read container-level descriptors, manage sample-level timing, adjust byte endianness or channel interleaving, and deliver the raw digital waveform directly to the audio rendering pipeline.

Container Parsing and FourCC Identification

The processing pipeline begins at the demuxer level. An MP4 container stores track metadata inside hierarchical structures called boxes (or atoms). The demuxer traverses down to the Sample Table Box (moov > trak > mdia > minf > stbl) and inspects the Sample Description Box (stsd).

Inside the stsd box, the demuxer reads the Four-Character Code (FourCC) that identifies the audio format. While MPEG-4 traditionally utilizes compressed codecs like AAC, standard extensions and modern specifications support PCM via specific FourCC identifiers:

  • Integer PCM: Often identified by codes such as ipcm, sowt (little-endian 16-bit integer), twos (big-endian 16-bit integer), in24, or in32.
  • Floating-Point PCM: Typically identified by codes like fpcm, fl32, or fl64.

Metadata Extraction and Track Configuration

Once the FourCC confirms uncompressed PCM, the decoder reads the audio sample entry inside the stsd box to configure the output format. It extracts key parameters required to interpret the raw bytes:

  • Channel Count: Number of discrete audio channels (e.g., 1 for mono, 2 for stereo, 6 for 5.1).
  • Sample Rate: Frequency of the audio samples (e.g., 44.1 kHz, 48 kHz, 96 kHz).
  • Bit Depth: Bit resolution per sample (e.g., 16-bit, 24-bit, 32-bit).

Data Extraction from Media Data (mdat)

The demuxer uses the sample table index boxes to locate the raw audio data within the Media Data Box (mdat):

  • Chunk Offsets (stco or co64): Defines the physical byte locations of audio data chunks in the file.
  • Sample Sizes (stsz or stz2): Defines the size of each audio sample.
  • Time-to-Sample (stts): Maps sample counts to durations, establishing accurate synchronization with the video stream.

Unlike compressed audio formats where samples correspond to variable-sized compressed frames, PCM samples are uniformly sized blocks of bytes directly correlated to time.

Bypassing Decompression and Signal Normalization

Because the audio is uncompressed, the decoder bypasses mathematical decompression stages (such as Modified Discrete Cosine Transform or Huffman decoding) used for codecs like AAC or MP3. Instead, the decoder acts as a stream conditioner and performs lightweight data preparation:

  1. Endianness Conversion: If the container stores samples in big-endian format (common in historical MP4/QuickTime implementations) and the host architecture is little-endian (such as x86 or ARM), the decoder swaps the byte order of each sample.
  2. Channel De-interleaving or Mapping: PCM data is typically stored interleaved (e.g., L-R-L-R). If the host operating system's audio output requires planar buffers (all Left samples followed by all Right samples) or specific channel assignments, the decoder reorganizes the memory layout.
  3. Format Casting: If necessary, integer PCM (e.g., 24-bit packed integer) is converted or padded to the native format preferred by the host audio API, such as 32-bit floating-point.

Output to Audio Hardware

After memory alignment and channel mapping, the decoder feeds the conditioned PCM sample buffers into the host platform's audio subsystem (such as ALSA/PulseAudio on Linux, CoreAudio on macOS/iOS, or WASAPI on Windows). The audio subsystem uses the sample rate and channel layout provided during the metadata extraction stage to play back the bit-perfect audio stream.
