How stts Boxes Define Variable Frame Rates in MP4

The Time-to-Sample (stts) box within an MPEG-4 (MP4) container is the primary metadata structure responsible for mapping individual media samples (video frames) to their respective display durations. By utilizing a compact, run-length encoded table of sample counts and time deltas, the stts box enables precise implementation of Variable Frame Rates (VFR). This mechanism allows an MP4 container to dynamically allocate varying display times to individual frames or groups of frames without altering the underlying raw video stream.

The Role and Hierarchy of the stts Box

In the ISO Base Media File Format (ISO/IEC 14496-12), which defines the architecture for MP4 files, timing and indexing information is organized hierarchically inside the movie header (moov).

The stts box resides within the Sample Table box (stbl):

moov ➔ trak ➔ mdia ➔ minf ➔ stbl ➔ stts

While other boxes define sample offsets (stco/co64), sizes (stsz), and synchronization points (stss), the stts box provides the foundational timeline for decoding and presenting frames.

Internal Structure of the stts Table

The stts box achieves compact storage through run-length encoding. Rather than listing every individual frame's duration independently, it groups consecutive frames that share the exact same duration into single entries.

The structure of the stts payload consists of:

  1. Version & Flags (4 bytes): Standard container metadata.
  2. Entry Count (32-bit unsigned integer): The total number of records in the time-to-sample table.
  3. Table Entries: A sequential array of records, where each record contains:
    • sample_count (32-bit integer): The number of consecutive samples that share the specified duration.
    • sample_delta (32-bit integer): The duration of each individual sample in the group, expressed in units of the media track's timescale (defined in the mdhd box).
+------------------------------------+
| Version (1 byte) | Flags (3 bytes) |
+------------------------------------+
| Number of Entries (4 bytes)       |
+------------------------------------+
| sample_count 1   | sample_delta 1  |
| sample_count 2   | sample_delta 2  |
| ...              | ...             |
+------------------------------------+

Defining Constant Frame Rate (CFR) vs. Variable Frame Rate (VFR)

The design of the stts table makes the distinction between CFR and VFR straightforward:

Constant Frame Rate (CFR)

In a CFR video, every frame has the exact same duration. As a result, the stts box contains only one entry for the entire video stream:

  • Timescale: 90000 (common for video)
  • Entry Count: 1
  • Entry 1: sample_count = 1800, sample_delta = 3000
  • Result: 1,800 frames, each lasting \(3000 / 90000 = 1/30\text{s}\) (a constant 30 fps for 60 seconds).

Variable Frame Rate (VFR)

In a VFR video, frames can have varying durations depending on content, scene complexity, screen recording pauses, or dropped frames during capture. The stts table handles this by defining multiple entries with different sample_delta values:

  • Timescale: 90000
  • Entry Count: 3
  • Entry 1: sample_count = 600, sample_delta = 3000 (30 fps for the first 20 seconds)
  • Entry 2: sample_count = 1200, sample_delta = 1500 (60 fps for the next 20 seconds)
  • Entry 3: sample_count = 240, sample_delta = 7500 (12 fps for the final 20 seconds)

By switching the sample_delta across segments or even for single isolated frames, the container accurately represents fluctuating frame rates.

Timestamp Calculation: DTS and PTS

The stts box directly calculates the Decode Time (DTS) for every frame sequentially:

\[\text{DTS}(n) = \text{DTS}(n-1) + \text{sample\_delta}(n-1)\]

The first frame always begins at \(\text{DTS}(0) = 0\). Subsequent decode timestamps are derived by cumulatively summing the sample_delta values.

When a stream uses B-frames (bi-directional predictive frames), the order in which frames are decoded differs from the order in which they are displayed. In this scenario, the stts box works in tandem with the Composition Time-to-Sample (ctts) box:

\[\text{PTS}(n) = \text{DTS}(n) + \text{ctts\_offset}(n)\]

  • stts sets the base decode timeline.
  • ctts applies sample-specific composition offsets to determine the actual Presentation Time (PTS).

Benefits of stts-Based VFR Management

  • Storage Efficiency: Run-length encoding ensures that sequences of steady frame rates consume minimal metadata space, expanding only when frame durations actively change.
  • Format Agnostic: The variable frame rate logic is maintained entirely within the MP4 container structure. The underlying compressed bitstream (such as H.264 or H.265 NAL units) does not need to embed proprietary container timing markers.
  • A/V Synchronization: Audio tracks generally run at fixed sample rates. The precise, timescale-based duration units of the stts box ensure that variable-rate video tracks remain strictly synchronized with continuous audio tracks throughout playback.
