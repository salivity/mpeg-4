Streaming Fragmented MP4 Over WebSockets

Streaming fragmented MPEG-4 (fMP4) over WebSocket protocols enables low-latency, bidirectional, and real-time media delivery directly to web browsers without the overhead of traditional chunk-based HTTP protocols. This article covers the core technical requirements needed to implement an fMP4 over WebSocket pipeline, spanning media encoding, container fragmentation, transport handling, and client-side decoding using modern web APIs.

1. Media Encoding and Container Structure

To stream MP4 data continuously without needing the entire file before playback begins, the media must be formatted into fragmented MP4 (fMP4) rather than standard progressive MP4:

  • Supported Codecs: The underlying audio and video streams must use browser-compatible codecs, commonly H.264 (AVC) or H.265 (HEVC) for video, and AAC or Opus for audio.
  • Initialization Segment (ftyp and moov boxes): The stream must produce an initial setup segment containing the File Type (ftyp) and Movie (moov) boxes. This segment carries track definitions and codec parameters but no actual media frames.
  • Media Segments (moof and mdat boxes): Following the initialization segment, media data is split into discrete fragments composed of a Movie Fragment box (moof) containing metadata and timeline information, and a Media Data box (mdat) containing the encoded samples.
  • Keyframe Alignment: Each fragment should ideally begin with an IDR (Instantaneous Decoder Refresh) keyframe to allow immediate decoding and clean recovery from dropped packets.

2. Server-Side Pipeline and Transport

The WebSocket server acts as the delivery mechanism for the raw binary stream and must manage how fragments are dispatched to clients:

  • Binary Data Transmission: WebSockets must be configured to send raw binary frames (Opcode 0x2) rather than base64-encoded text or JSON to prevent transport overhead.
  • Initialization Delivery: The server must cache the initialization segment (ftyp + moov) and immediately transmit it to any new client that establishes a connection before sending subsequent moof + mdat pairs.
  • Stream Multiplexing: Audio and video can be multiplexed into a single fMP4 stream or delivered across separate tracks. If separated, the client must manage synchronized playback pipelines.
  • Flow Control and Backpressure: The server must handle varying network speeds by monitoring socket buffer health, dropping non-keyframe segments if a client falls behind to maintain low latency.

3. Client-Side Playback Architecture

Modern browsers cannot natively play a continuous fMP4 stream directly from a standard HTML5 <video> source URL without bridging APIs:

  • WebSocket Configuration: The client WebSocket instance must set its binaryType property to 'arraybuffer' to receive raw chunks directly.
  • Media Source Extensions (MSE): The client must use the MediaSource API to attach a custom media stream to an HTML <video> element.
  • SourceBuffer Management:
    • A SourceBuffer is created with the exact MIME type and codec string matching the stream (for example, video/mp4; codecs="avc1.42E01E, mp4a.40.2").
    • The received binary chunks must be queued and passed to the SourceBuffer.appendBuffer() method sequentially, ensuring no new appends occur while the buffer's updating flag is true.
  • Buffer Eviction: For long-running live streams, the client must periodically remove older media segments from the SourceBuffer using remove() to avoid exhausting device memory.
