Understanding MP4 Sample to Chunk Box stsc

The MPEG-4 (MP4) container format organizes media data into discrete units called samples, which are grouped into contiguous blocks called chunks to optimize storage and indexing. This article explains how the Sample-to-Chunk box (stsc), located within the track sample table (moov.trak.mdia.minf.stbl.stsc), maps individual media samples to chunks, how this data interacts with other index boxes to locate exact file byte offsets, and how the operating system subsequently translates those offsets into physical disk sectors.

The Role of Chunks in MP4 Containers

In the ISO Base Media File Format (ISOBMFF/MPEG-4 Part 14), storing a distinct file offset for every individual video frame or audio packet would create massive file headers. To minimize metadata overhead, the format groups adjacent samples into "chunks."

While chunk positions are stored in the Chunk Offset box (stco for 32-bit offsets or co64 for 64-bit offsets), the container requires a mechanism to determine which samples belong to which chunk. This is the sole function of the stsc (Sample-to-Chunk) box.

Structure of the stsc Box

The stsc box uses a run-length encoded table to keep metadata compact. Each entry in the table represents a range of chunks that share the same configuration.

An stsc entry contains three primary fields:

  • first_chunk: The starting chunk index for this run.
  • samples_per_chunk: The number of consecutive media samples contained in each chunk in this run.
  • sample_description_index: The index pointing to the codec configuration entry in the Sample Description box (stsd).

A run continues until a new entry specifies a different first_chunk. For example:

Entry first_chunk samples_per_chunk sample_description_index
1 1 5 1
2 4 3 1

In this scenario:

  • Chunks 1, 2, and 3 each contain 5 samples.
  • Chunk 4 and all subsequent chunks contain 3 samples (until another entry appears).

Mapping a Sample to an Absolute Byte Offset

Locating a specific sample (for example, Sample \(N\)) requires decoding multiple boxes in the sample table (stbl):

  1. Find the Containing Chunk via stsc: Iterate through the stsc table, accumulating sample counts per chunk until reaching Sample \(N\). This identifies the target chunk index (\(C\)) and the sample’s relative index within that chunk (\(S_{rel}\)).

  2. Retrieve the Base Chunk Offset via stco/co64: Look up chunk \(C\) in the Chunk Offset table. This yields the absolute byte position where chunk \(C\) begins in the file (\(Offset_{chunk}\)).

  3. Calculate Intra-Chunk Offset via stsz: Look up the sizes of all samples inside chunk \(C\) that precede \(S_{rel}\) using the Sample Size box (stsz or stz2). Sum these sizes to determine the relative offset (\(Offset_{rel}\)).

  4. Compute Final Byte Offset: \[\text{Byte Offset} = Offset_{chunk} + Offset_{rel}\]

Translating File Byte Offsets to Disk Sectors

Once the media demuxer calculates the exact byte offset of the target sample:

  1. Filesystem Resolution: The media player makes a system call (such as pread or ReadFile) requesting data at the calculated byte offset. The filesystem looks up its allocation table (such as an ext4 inode extent tree or NTFS B-tree) to determine which logical block corresponds to that file offset.
  2. Block-to-Sector Translation: The filesystem block address is translated into a Logical Block Address (LBA) representing physical storage sectors (typically 512 bytes or 4096 bytes/Advanced Format).
  3. Sector Read: The storage controller retrieves the specific physical sectors hosting the data and loads the sample directly into memory for decoding.
