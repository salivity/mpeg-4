How MP4 Stores Multi-DRM Keys via the PSSH Box

This article explains how the MPEG-4 (ISOBMFF) container format utilizes the Protection System Specific Header (pssh) box to enable multi-DRM streaming. By pairing Common Encryption (CENC) with distinct pssh metadata structures, a single encoded video file can store initialization data for multiple Digital Rights Management (DRM) technologies—such as Google Widevine, Microsoft PlayReady, and Apple FairPlay—allowing different client devices to retrieve the necessary decryption keys from their respective license servers without requiring separate media files.

The Role of Common Encryption (CENC)

Standard MPEG-4 (ISO/IEC 14496-12) containers support multi-DRM through the ISO/IEC 23001-7 Common Encryption (CENC) standard. CENC decouples the encryption algorithm from the key management and license acquisition process. The underlying media samples are encrypted using standard AES-128 encryption (commonly in cenc counter mode or cbcs cipher block chaining mode). Because the encryption format is universal, the media payload is identical regardless of which DRM system decrypts it.

The DRM-specific parameters needed to decrypt the media—such as license server endpoints, key identifiers, and proprietary authentication payloads—are encapsulated inside the pssh box within the container metadata.

Structure of the pssh Box

The pssh box resides within the initialization metadata of the container (inside the moov box) or within individual movie fragments (inside the moof box). Its binary layout is structured as follows:

  • Box Header: Defines the standard 4-byte size and 4-byte box type (pssh).
  • Version and Flags (4 bytes): Specifies the pssh format version (typically 0 or 1) and associated flags.
  • SystemID (16 bytes / 128-bit UUID): Identifies the specific DRM system that can read and process the contents of this box.
  • KID Count and Key IDs (Version 1 only): A list of 16-byte Key Identifiers (KIDs) indicating the exact keys needed to decrypt the associated tracks.
  • Data Size (4 bytes): The length of the proprietary DRM payload.
  • Data (Variable length): The opaque initialization blob required by the specific DRM system's Content Decryption Module (CDM).

Multi-DRM Implementation with Distinct SystemIDs

To achieve multi-DRM support, an MP4 packager generates multiple pssh boxes and concatenates them in the container. Each pssh box contains the unique 128-bit SystemID corresponding to a supported DRM platform:

  • Google Widevine: edef8ba9-79d6-4ace-a3c8-27dcd51d21ed
  • Microsoft PlayReady: 9a04f079-9840-4286-ab92-e65be0885f95
  • Apple FairPlay: 94ce86fb-07ff-4f43-adb8-93d2fa968ca2
  • Clear Key: e2719d58-a985-b3c9-781a-b030af78d30e

While each box references the same standard Key IDs (KIDs), the Data field contains information tailored solely to that specific DRM ecosystem. For instance, the PlayReady pssh box stores a WRMHEADER XML or binary structure containing license acquisition URLs and rights rules, whereas the Widevine pssh box stores a Protocol Buffer payload containing provider settings and content IDs.

Client-Side Processing and Key Retrieval

When a media player loads the MP4 file or DASH/HLS init segment:

  1. Extraction: The player's demuxer scans the container and extracts all present pssh boxes.
  2. Matching: The player checks the client device's supported DRM capabilities and selects the pssh box matching the native CDM’s SystemID (e.g., Widevine in Google Chrome or PlayReady in Microsoft Edge).
  3. Challenge Generation: The selected pssh payload is passed to the browser's Encrypted Media Extensions (EME) or native CDM API as initialization data (initData). The CDM uses this data to generate a cryptographic license challenge.
  4. License Acquisition: The player sends the challenge to the appropriate DRM license server, which authenticates the request and returns the AES content keys wrapped in a secure license.
  5. Decryption: The CDM loads the AES keys and decrypts the standard CENC media samples for playback.
