MPEG-4 Sample Encryption with the senc Box

This article provides an overview of how the MPEG-4 ISO Base Media File Format (ISOBMFF) handles sample-level encryption through the Sample Encryption Box (senc). It covers the role of the senc box within the Common Encryption (CENC) standard, its internal binary structure, the handling of Subsample Encryption, and how it coordinates with related boxes to enable secure, byte-accurate media decryption.

The Role of the senc Box in Common Encryption

In the MPEG-4 Common Encryption standard (ISO/IEC 23001-7), encryption is applied at the sample (individual frame or access unit) level rather than encrypting the entire container file. This architecture allows container metadata, track headers, and timing information to remain in the clear for smooth demuxing and streaming.

The senc box is the dedicated container for per-sample encryption parameters. While static parameters—such as the Key Identifier (KID), encryption scheme, and default Initialization Vector (IV) size—are defined at the track level in the Track Encryption Box (tenc), dynamic parameters that change per sample are stored inside the senc box.

Structure of the senc Box

The senc box is defined as a FullBox, meaning it includes standard 4-byte version and flags fields followed by the sample encryption details:

  1. Box Header: Contains standard size and four-character code 'senc'.
  2. Version and Flags: A 1-byte version and a 3-byte flags field. The primary flag is 0x000002 (SubsampleEncryption), which indicates whether the box contains subsample-level mapping.
  3. Sample Count: A 32-bit integer indicating the number of media samples described within the box.
  4. Sample Entries: An array of per-sample structures containing:
    • Initialization Vector (IV): A byte array (typically 8 or 16 bytes, as dictated by the track header) unique to the specific sample.
    • Subsample Mapping (Optional): Included only if the 0x000002 flag is set.

Handling Subsample Encryption

Most modern streaming codecs (such as H.264/AVC and H.265/HEVC) require NAL unit headers and slice headers to remain unencrypted so that decoders and parsers can read structural slice data without decrypting the payload. To achieve this, the senc box supports Subsample Encryption.

When subsample encryption is active, each sample entry includes:

  • subsample_count: A 16-bit integer denoting the number of subsample ranges in the sample.
  • Subsample Map Array: A sequence of pairs:
    • BytesOfClearData (16-bit integer): The number of unencrypted bytes at the start of the subsample.
    • BytesOfProtectedData (32-bit integer): The number of encrypted bytes that immediately follow the clear bytes.

A single video frame can contain multiple subsamples. A decryptor iterates through each pair, skipping the clear bytes and decrypting only the protected bytes using the designated IV and cipher mode.

Integration with saiz and saio Boxes

In fragmented MP4 (fMP4) files commonly used in adaptive streaming (HLS and DASH), the encryption data inside the senc box is often indexed using the Sample Auxiliary Information Sizes (saiz) and Sample Auxiliary Information Offsets (saio) boxes:

  • saiz: Specifies the exact size (in bytes) of the encryption metadata for each sample.
  • saio: Provides byte offsets pointing directly to the location of the senc data within the moov or moof (Movie Fragment) boxes.

This indexing structure allows demuxers and media engines to locate and read the required IV and subsample map rapidly without parsing the entire container payload sequentially.

The Decryption Process Flow

When an MPEG-4 player encounters an encrypted track using senc:

  1. Parameter Initialization: The player extracts the encryption scheme (e.g., cenc for AES-CTR or cbcs for AES-CBC with pattern protection) and default Key ID from the tenc box.
  2. Key Retrieval: The DRM system retrieves the decryption key matching the Key ID.
  3. Sample Parsing: For each sample, the demuxer reads the IV from the senc box (or via saio/saiz offsets).
  4. Range Application: If subsamples are present, the decryptor processes the clear/protected byte map, applying the AES decryption key and sample IV exclusively to the protected byte ranges.
  5. Decoder Hand-off: The assembled, unencrypted sample data is passed downstream to the media decoder.
