MPEG-4 Atom Nesting Rules and Structure

The MPEG-4 (MP4) file format relies on the ISO Base Media File Format (ISOBMFF), which organizes all media and metadata into hierarchical building blocks called atoms (or boxes). This article outlines the fundamental structural rules that govern how child atoms are nested within parent container atoms, including header specifications, size calculations, boundary constraints, and hierarchical ordering.

The Atom Header and Payload Layout

Every atom consists of a header followed by a payload. The standard header is 8 bytes long:

  • Size (4 bytes): An unsigned 32-bit integer indicating the total size of the atom in bytes, including the header.
  • Type (4 bytes): A Four-Character Code (FourCC) identifying the atom (e.g., moov, trak, mdat).

If the 32-bit size is set to 1, an optional 8-byte extended size field (largesize) immediately follows the type, enabling 64-bit addressing for atoms larger than 4 GB.

Container Atoms vs. Leaf Atoms

Atoms are structurally classified into two main categories:

  1. Leaf Atoms: These contain actual payload data, such as media chunks, codec configurations, or metadata properties (e.g., mvhd, hdlr, stsz). They cannot contain child atoms.
  2. Container (Parent) Atoms: These hold no raw data payload of their own. Instead, their entire payload area consists solely of a contiguous sequence of child atoms (e.g., moov, trak, mdia, minf, stbl). Some hybrid atoms (often called "full boxes") include header flags or versioning bytes before the sequence of child atoms begins.

Boundary and Size Consistency Rules

When nesting child atoms within a parent container, strict size arithmetic applies:

  • Total Size Match: The size declared in a parent atom's header must equal the size of the parent's own header plus the sum of the total sizes of all nested child atoms.
  • Boundary Enforcement: A child atom must start at an offset within the parent's payload and cannot extend past the end of the parent atom. The formula Child_Offset + Child_Size <= Parent_Offset + Parent_Size must hold true for every nested atom.
  • Zero Size Exception: A size value of 0 in an atom header signifies that the atom extends to the end of the file. This rule is only valid for top-level atoms (such as mdat) and is illegal for nested child atoms, as a nested atom with size 0 would prevent parsers from determining where the parent atom ends.

Hierarchical Tree Structure and Ordering

Nesting must strictly follow the tree hierarchy defined by ISO/IEC 14496-12. Key rules include:

  • Strict Lineage: Certain atoms can only exist within specific parents. For example, a Sample Table atom (stbl) must be a child of Media Information (minf), which must reside inside Media (mdia), which belongs inside Track (trak), which belongs inside Movie (moov).
  • Sequential Precedence: Inside certain containers, specific child atoms must appear before others. For instance, the Movie Header atom (mvhd) must be the first child inside moov, and the Track Header atom (tkhd) must be the first child inside trak.
  • Contiguity: Child atoms inside a parent container must be laid out contiguously without unindexed padding or raw gaps between them.

Parser Traversal and Unknown Atom Handling

A parser navigates container atoms by reading each child's size and FourCC type sequentially until the parent's defined byte boundary is reached. If an unrecognized atom type is encountered inside a container, standard-compliant parsers use the atom's size header to skip its payload entirely, moving directly to the start of the next sibling atom without invalidating the rest of the parent's structure.
