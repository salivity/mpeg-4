How CENC Standardizes MPEG-4 Decryption Workflows

Common Encryption (CENC) standardizes decryption workflows across disparate MPEG-4 client platforms by separating the content encryption mechanism from the Digital Rights Management (DRM) key management systems. Defined under ISO/IEC 23001-7, CENC allows content providers to encrypt video and audio tracks once using standard Advanced Encryption Standard (AES) ciphers, while enabling multiple native DRM systems—such as Google Widevine, Microsoft PlayReady, and Apple FairPlay—to decrypt the exact same media files on different operating systems and hardware platforms.

Decoupling Encryption from DRM Systems

Prior to CENC, each proprietary DRM system required its own unique encryption algorithm, container format, and packaging pipeline. CENC eliminates this fragmentation by establishing a uniform encryption layer.

The standard mandates standard AES 128-bit encryption operating in either Counter (CTR) mode (identified as the cenc protection scheme) or Cipher Block Chaining (CBC) with 10% pattern protection (identified as the cbcs protection scheme). Because the encryption algorithm is fixed and universal, the underlying media payload is identical regardless of which client platform plays it back.

Standardized Metadata Signaling in the ISO Base Media File Format

CENC establishes a standardized set of metadata boxes within the ISO Base Media File Format (ISOBMFF / MP4) container to instruct client devices how to handle decryption:

  • Protection System Specific Header (pssh) Box: Contains DRM-specific metadata required by a client's Content Decryption Module (CDM) to request and acquire the decryption key. A single MP4 container or manifest can hold multiple pssh boxes side by side, each carrying a unique SystemID corresponding to a specific DRM vendor (e.g., Widevine, PlayReady).
  • Track Encryption (tenc) Box: Defines default encryption parameters for an entire track, such as the default Key ID (KID), encryption scheme, and initialization vector (IV) size.
  • Sample Encryption (senc) and Sample Auxiliary Information (saio/saiz) Boxes: Provide sample-specific data, including initialization vectors and sub-sample encryption maps that delineate clear (unencrypted) headers from encrypted payload bytes.

The Unified Client Decryption Workflow

When an MPEG-4 client encounters a CENC-packaged stream, the decryption process follows a consistent, platform-independent workflow:

  1. Metadata Parsing: The client's media demuxer parses the container and extracts the standard CENC boxes (tenc, senc) along with the pssh box matching the platform's supported DRM SystemID.
  2. License Acquisition: The demuxer passes the DRM-specific initialization data from the selected pssh box to the client’s native Content Decryption Module (CDM) via standard APIs (such as Encrypted Media Extensions in web browsers). The CDM contacts the appropriate DRM license server to retrieve the content encryption key associated with the Key ID.
  3. Key Provisioning to Hardware: The CDM unwraps the license and securely loads the raw content key into the device’s hardware-level cryptographic engine or Trusted Execution Environment (TEE).
  4. Standardized Decryption: The media engine feeds the encrypted elementary stream, along with the sample encryption parameters (IVs and sub-sample offsets from the senc box), to the decryption engine. The engine decrypts the samples using the standard AES cipher and routes the uncompressed data directly to the secure video pipeline.

Multi-DRM Efficiency

By standardizing container signaling, cipher modes, and sample-level metadata, CENC allows streaming services to encode, package, and cache a single set of MPEG-4 media assets. Disparate client platforms utilize their native, hardware-optimized DRM systems solely for key exchange and authentication, while relying on a unified cryptographic process to decrypt and render the media.
