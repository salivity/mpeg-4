How MP4 Files Support 64-Bit Offsets Over 4GB

This article explains how the MPEG-4 file format overcomes the traditional 4-gigabyte file size limit through 64-bit addressing mechanisms. By replacing standard 32-bit chunk offset tables with 64-bit counterparts and utilizing 64-bit box header extensions, the ISO Base Media File Format allows multimedia files to scale seamlessly into multi-gigabyte and multi-terabyte sizes.

The 4-Gigabyte Barrier in Standard MP4

The MPEG-4 Part 14 (MP4) container format is based on the ISO Base Media File Format (ISO/IEC 14496-12). In its original specification, the format relied on 32-bit unsigned integers for both box (atom) lengths and media chunk offsets.

Because a 32-bit unsigned integer can address a maximum of \(2^{32} - 1\) bytes (approximately 4.29 gigabytes), any file exceeding this threshold breaks standard parsing:

  • The byte offsets pointing to media data wrap around or overflow.
  • Container boxes, such as the Media Data box (mdat), cannot describe a size larger than 4 GB using a 32-bit integer.

To overcome these constraints, the specification introduced two key structural adaptations: 64-bit chunk offset boxes (co64) and 64-bit box headers.

1. The co64 (Chunk Large Offset) Box

In an MP4 file, sample data is stored in the mdat box, while timing and location metadata reside in the moov box. The sample table (stbl) maps where individual frames or samples are located on the disk.

In standard files under 4 GB:

  • The stco (Chunk Offset Box) contains a table of 32-bit integers. Each entry defines the absolute byte offset from the beginning of the file to a specific chunk of media data.

For files that exceed 4 GB:

  • The stco box is replaced by the co64 (Chunk Large Offset Box).
  • The co64 box has the exact same structure as the stco box, except each offset entry is an 8-byte (64-bit) unsigned integer instead of a 4-byte (32-bit) integer.
  • This expands the addressing limit to \(2^{64} - 1\) bytes (approximately 18.4 exabytes), allowing media chunks located past the 4 GB mark to be indexed accurately.

A track cannot contain both stco and co64 simultaneously; an MP4 demuxer checks the four-character code (FourCC) within the sample table box hierarchy (moov \(\rightarrow\) trak \(\rightarrow\) mdia \(\rightarrow\) minf \(\rightarrow\) stbl) to determine whether it should read 32-bit or 64-bit offsets.

2. 64-Bit Box Headers (largesize)

In addition to pointing to offsets past 4 GB, individual boxes—most notably the mdat box containing the actual video and audio payloads—frequently exceed 4 GB themselves.

Standard MP4 box headers use an 8-byte layout:

  • 4 bytes: Box size (uint32)
  • 4 bytes: Box type (FourCC, e.g., mdat)

When a box exceeds \(2^{32} - 1\) bytes:

  1. The initial 4-byte size field is set to 1 (which acts as a special flag).
  2. The 4-byte type follows as usual.
  3. An additional 8-byte largesize field (uint64) is inserted immediately after the type.

When a parser encounters a box size of 1, it reads the following 64-bit field to calculate the actual total length of the box, accommodating media payloads of virtually unlimited size.

Summary of Parsing Flow

When a media player or demuxer parses an MP4 larger than 4 GB:

  1. It encounters an mdat box with a 32-bit size value set to 1 and reads the subsequent 64-bit largesize value to handle the container boundary.
  2. It navigates to the metadata index (moov), drills down to the sample table (stbl), and identifies the co64 atom.
  3. It reads the array of 64-bit absolute offsets from co64 to retrieve and decode media samples stored beyond the 4 GB boundary.
