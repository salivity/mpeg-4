RTSP Session Control for MPEG 4 Media Servers

The Real-Time Streaming Protocol (RTSP) acts as a network control protocol designed to establish and manage multimedia sessions between client endpoints and media streaming servers. In the context of MPEG-4 streaming, RTSP does not transport the actual audio or video payload; instead, it functions as a "network remote control." By leveraging stateful request-response commands, RTSP controls stream parameters, allocates transport channels, and coordinates the playback states of MPEG-4 video and audio streams.

The Role of RTSP in Media Streaming

RTSP operates at the application layer, typically over TCP port 554 for reliable delivery of control messages. It manages the lifecycle of a media session while delegating the actual delivery of MPEG-4 media packets to transport protocols:

  • RTP (Real-time Transport Protocol): Carries the packetized MPEG-4 elementary streams (such as H.264/AVC video and AAC audio).
  • RTCP (RTP Control Protocol): Monitors transmission statistics and quality of service (QoS), aiding in media synchronization.
  • RTSP (Real-Time Streaming Protocol): Maintains the session state, interprets user commands, and manages transmission parameters.

Step-by-Step Session Control Workflow

RTSP manages MPEG-4 media sessions using a sequence of standardized request methods. Each session moves through distinct states: Init, Ready, and Playing.

1. Discovery and Description (DESCRIBE)

The client initiates contact by sending a DESCRIBE request containing the URL of the requested MPEG-4 file or stream.

  • The server responds with a Session Description Protocol (SDP) payload.
  • The SDP data defines the media characteristics, including codecs (e.g., MPEG-4 Part 2 or Part 10/H.264), clock rates, stream URLs for separate audio/video tracks, and payload types.

2. Stream Allocation and Session Creation (SETUP)

Before streaming begins, the client issues a SETUP request for each media track (audio and video) specified in the SDP.

  • The request specifies the transport mechanism (e.g., UDP unicast/multicast or interleaved TCP) and local client ports for RTP and RTCP.
  • The server allocates necessary transmission resources, binds its own RTP/RTCP ports, and assigns a unique Session identifier.
  • The session transitions to the Ready state.

3. Playback Management (PLAY and PAUSE)

Once configured, the client controls media flow dynamically:

  • PLAY Request: Instructs the server to begin sending MPEG-4 data via RTP. The request can include a Range header to seek to specific timestamps or adjust playback speed. The session enters the Playing state.
  • PAUSE Request: Halts RTP packet delivery temporarily without closing the session. Server-side session state and allocated ports remain active, allowing immediate resumption via a subsequent PLAY command.

4. Session Termination (TEARDOWN)

When playback finishes or the user disconnects, the client sends a TEARDOWN request using the active Session ID.

  • The server immediately halts all RTP/RTCP transmissions for that session.
  • All associated network sockets, buffers, and state resources allocated for the MPEG-4 stream are freed.

Session State Tracking

Unlike stateless protocols like HTTP, RTSP maintains a state machine on both the client and server. The server tracks each active MPEG-4 stream using the unique Session header generated during the SETUP phase. Every subsequent command (PLAY, PAUSE, TEARDOWN, or parameter adjustments via SET_PARAMETER) must include this Session ID, ensuring accurate synchronization and delivery of separate MPEG-4 tracks over the life of the connection.
