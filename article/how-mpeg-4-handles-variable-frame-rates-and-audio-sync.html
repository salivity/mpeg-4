How MPEG-4 Handles Variable Frame Rates and Audio Sync

An MPEG-4 (MP4) container seamlessly supports dynamic, variable frame rate (VFR) video without losing audio synchronization by abandoning fixed-interval assumptions in favor of timestamp-based scheduling. Instead of relying on a constant frame duration, the container uses internal metadata tables to assign precise durations and presentation timestamps to every individual video frame. Because both the audio and video tracks reference an independent, shared master timebase, fluctuations in video frame delivery have zero impact on the continuous playback of the audio stream.

Independent Track Timebases and Master Clock

Inside the MP4 container structure (based on the ISO Base Media File Format), audio and video exist as separate tracks (trak boxes). Each track defines its own media header (mdhd), which sets a specific time scale—the number of time units (clock ticks) that pass per second.

A video track might use a time scale of 90,000 units per second, while an audio track might use 48,000 units per second (matching a 48 kHz sampling rate). The container maps these independent track rates back to a unified movie timeline (mvhd). Because the media player references this global master clock, it does not rely on video frame counts to measure elapsed time.

Time-to-Sample Tables (stts)

For constant frame rate (CFR) video, every frame has the same duration. For dynamic or variable frame rate (VFR) video, frame durations vary. The MP4 container handles this via the Time-to-Sample table (stts) located in the sample table box (stbl).

The stts table stores entries consisting of:

  • Sample Count: How many consecutive frames share the same duration.
  • Sample Delta: The exact duration of each frame, measured in track timescale ticks.

When a scene changes from 60 fps to 24 fps, or drops frames due to bandwidth or rendering constraints, the container simply creates a new entry in the stts table with a larger delta value. The player reads this table and waits the specified number of clock ticks before displaying the next frame.

Decoding vs. Presentation Timestamps (stts and ctts)

Modern video codecs (such as H.264 and H.265) utilize out-of-order frame decoding with I, P, and B-frames. To keep dynamic frame rates aligned:

  1. Decoding Time Stamps (DTS): Calculated sequentially using the stts table to determine when the decoder must process a frame.
  2. Composition Time Offset (ctts): Calculates the Presentation Time Stamp (PTS) by adding an offset to the DTS. The PTS dictates the exact moment a frame must appear on screen.

Audio frames typically decode and present in the same linear order. As long as a video frame's PTS matches the current playback clock, it renders at the correct moment relative to the audio's PTS.

How Desynchronization Is Prevented

Audio desynchronization typically occurs in primitive formats that calculate time by multiplying the frame number by a static frame rate (e.g., Frame Index / 29.97). If frames are missing or variable, the calculation drifts.

In an MP4 container:

  • The audio buffer outputs continuously according to the audio clock.
  • The video renderer continuously queries the master clock and displays the frame whose PTS matches that clock.
  • If the video frame rate fluctuates, drops, or spikes, each frame still displays only at its designated PTS mark.

By handling media as a sequence of uniquely timed packets tied to a standardized clock rather than a continuous stream of fixed intervals, the MP4 container guarantees perfect audio-video alignment under any frame rate condition.
