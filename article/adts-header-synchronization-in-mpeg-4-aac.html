ADTS Header Synchronization in MPEG-4 AAC

The Audio Data Transport Stream (ADTS) format enables seamless playback and mid-stream synchronization in MPEG-4 Advanced Audio Coding (AAC) by embedding a dedicated metadata header before every audio frame. This article explains how the structural components of the ADTS header—including the syncword, stream configuration parameters, and frame length fields—allow decoders to locate audio boundaries, configure playback settings on the fly, and recover rapidly from data loss or transmission errors.

The Syncword: Locating Frame Boundaries

At the beginning of every ADTS header lies a 12-bit sequence known as the syncword, represented in binary as 1111 1111 1111 (or hexadecimal 0xFFF). Because ADTS streams are often transmitted over unreliable networks or broadcast channels without separate container metadata, decoders continuously scan the incoming bitstream for this specific 12-bit pattern to identify the potential start of a new audio frame.

Mid-Stream Configuration via Header Metadata

Unlike formats that require an initial global header (such as an MP4 container's moov atom), the ADTS header is self-contained and repeated for every frame. Directly following the syncword, the header provides critical decoding parameters:

  • MPEG Version: Identifies whether the stream is MPEG-2 or MPEG-4 AAC.
  • Profile: Specifies the AAC profile (e.g., AAC Main, LC, or SSR).
  • Sampling Frequency Index: Defines the sample rate of the audio data.
  • Channel Configuration: Dictates the channel layout (such as mono, stereo, or 5.1 surround).

Because these parameters appear with each frame, a decoder tuning into a live stream mid-broadcast can immediately configure its internal decoding pipeline and begin playback without waiting for a separate metadata packet.

False-Positive Protection Using Frame Length

Because audio payload data can randomly contain the 12-bit sequence 1111 1111 1111, decoders must verify that a detected syncword is authentic. The ADTS header includes a 13-bit frame length field indicating the total size of the header plus the audio data block.

To confirm synchronization:

  1. The decoder detects a syncword and reads the frame_length value.
  2. It offsets its read pointer by that exact number of bytes.
  3. It checks whether another valid syncword exists at the new position.

If the subsequent syncword is verified across multiple consecutive frames, the decoder locks synchronization. If not, the decoder treats the initial match as a false positive within the payload and resumes scanning.

Error Detection with CRC

The header contains a protection_absent flag. If this bit is set to 0, a 16-bit Cyclic Redundancy Check (CRC) field is appended to the header. This allows the decoder to validate data integrity. If a frame is corrupted during transmission, the decoder can discard the damaged frame and jump immediately to the next frame boundary, preventing audio distortion while maintaining timing synchronization.
