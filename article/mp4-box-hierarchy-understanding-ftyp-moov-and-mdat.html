MP4 Box Hierarchy: Understanding ftyp, moov, and mdat

In the MPEG-4 (MP4) container format, defined by the ISO Base Media File Format (ISOBMFF), the ftyp, moov, and mdat boxes are the three fundamental components that define compatibility, metadata, and media payload. Hierarchically, these three atoms exist as sibling root-level boxes residing directly in the file's primary directory rather than being nested within one another. This article breaks down the architectural relationship among these boxes, explains how their internal data links together, and details why their physical ordering dictates media playback behavior.

Sibling Root-Level Structure

In an MP4 container, every data block is encapsulated in a structure called a "box" (historically known as an "atom"). The ftyp, moov, and mdat boxes operate at the exact same hierarchical level: the file root.

[MP4 File Root]
 ├── ftyp (File Type Box)
 ├── moov (Movie Box / Metadata)
 └── mdat (Media Data Box / Raw Payload)

None of these three boxes is a parent or child of another. Instead, they divide the file's duties into identification, indexing, and raw data storage.

Individual Box Functions

  • ftyp (File Type Box): Identifies the file specification, major brand, minor version, and compatible brands. It tells the parser which specifications the file complies with (such as isom, mp42, or qt ).
  • moov (Movie Box): Acts as the master metadata container. It does not contain raw audio or video streams; instead, it houses the structural blueprint of the presentation.
  • mdat (Media Data Box): Serves as the storage payload containing the raw, encoded audio, video, subtitle frames, and other stream samples.

The Internal Hierarchy of the moov Box

While ftyp and mdat are structurally flat, the moov box contains an extensive nested hierarchy of child and grandchild boxes that map directly to the content inside mdat:

  • mvhd (Movie Header Box): Defines presentation-level details like duration, timescale, and creation time.
  • trak (Track Box): Contains metadata for an individual track (e.g., video or audio). A file typically has one trak per stream.
    • tkhd (Track Header Box): Specifies track dimensions, volume, and track ID.
    • mdia (Media Box): Declares information about the media data within the track.
      • minf (Media Information Box): Houses handler-specific information.
        • stbl (Sample Table Box): The critical indexing structure. It contains sub-boxes like stts (time-to-sample), stsz (sample sizes), stsc (sample-to-chunk), and stco / co64 (chunk offsets).

The Logical Relationship Between moov and mdat

The primary relationship between moov and mdat is referential. The mdat box contains raw, unindexed bytes. The sample table (stbl) inside the moov hierarchy acts as an index table pointing into the mdat payload:

  1. The stco (or 64-bit co64) box inside moov stores exact byte offsets pointing to the start of data chunks inside mdat.
  2. The stsz box specifies the exact byte length of each sample within those chunks.
  3. The media player reads moov to build an index, calculates the required byte range, and directly accesses the target frames located in mdat.

Without moov, the contents of mdat cannot be decoded or positioned in time. Without mdat, the moov box is simply an empty index.

Physical Sequence and Streaming Implications

Although ftyp, moov, and mdat are hierarchical peers, their physical order in the byte stream determines how the file can be processed:

  • ftyp First: By specification, the ftyp box must appear at the very beginning of the file so media decoders can immediately verify compatibility.
  • moov Before mdat (Fast-Start / Web Optimized): Placing the metadata (moov) ahead of the media payload (mdat) allows web browsers to download the index immediately. The player can calculate durations, display the first frame, and begin progressive playback without downloading the entire file.
  • mdat Before moov (Standard Recording): When recording live video, the final sizes and offsets of chunks are unknown until encoding finishes. Encoders write the mdat payload in real time and append the completed moov index at the end of the file once recording stops. Files formatted this way must be completely downloaded before playback can begin unless optimized using post-processing tools.
